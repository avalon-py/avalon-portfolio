The browser only talks to Vercel, and Vercel talks to the VM. That keeps the VM address and API key server-side and avoids CORS on the API. Behind the API, on the same Docker network, sit the data and training services:

Oracle Cloud VM

Everything backend runs on a single Always Free Ampere A1 VM (arm64), managed by one Docker Compose file: Caddy, the API, Postgres, MinIO, and the three Airflow services, plus a worker image that Airflow launches for each task. PyTorch is installed from the CPU-only wheel index, since the VM has no GPU.

What is public: only ports 80 and 443, opened in Oracle's security list and served by Caddy.

What is not: Postgres, MinIO and the Airflow UI are bound to 127.0.0.1, so they can only be reached from the VM itself (for example through an SSH tunnel).

Code moves through GitHub: I edit on my laptop, push, and run git pull and docker compose up -d --build on the VM. Secrets live in a .env file that exists only on the VM. Trained model bundles are written by the training task into a folder that the API container mounts read-only, so a retrain never needs an image rebuild.

Caddy: HTTPS and the front door

Caddy is the only container that listens on the internet. It gets and renews an HTTPS certificate on its own, then applies three rules before anything reaches the model:

<your-domain> {
    @no_key {
        path /predict
        not header X-Api-Key {$PREDICT_KEY}
    }
    respond @no_key 401

    request_body {
        max_size 5MB
    }

    reverse_proxy api:8000
}

/predict needs the shared secret in the X-Api-Key header (the Vercel proxy adds it), uploads over 5 MB get a 413, and everything else is forwarded to the api container by its Compose service name. /health stays open for monitoring. I tested each rule with curl: 401 without the key, 413 for a 6 MB body, and a pass-through to FastAPI otherwise.

Retraining and promotion

An Airflow pipeline ingests new videos from the YouTube API, embeds them, retrains, and checks for drift. A new model replaces the live one only if it passes two gates.

Hard gate: it must beat a simple linear baseline on the trailing average.

Soft gate: a paired bootstrap on the difference in Spearman correlation against the live model. It is rejected only if it is confidently worse, so ties go to the model trained on newer data.

Concretely, the bootstrap resamples the test rows 2,000 times and compares both models on the same rows. The new model is rejected only if the top of the 95% interval falls below -0.01. Every decision, promoted or not, is logged with its reason. After a promotion, the DAG restarts the API container so it loads the new bundle.

Serving

FastAPI loads one exported bundle (weights, scalers, column order, encoder config), and a test checks that serving reproduces the training path. It runs on an Oracle Cloud VM behind Caddy, with a Next.js front end on Vercel and per-IP rate limiting.

The API is stateless: it loads the bundle once at startup and answers from memory. Serving is CLIP-only, and a bundle trained with a different encoder is rejected when it loads. Feature code for a single request is a second implementation of the training math, which is why the parity test exists, and CI runs a smoke test of /health and /predict on every push.
